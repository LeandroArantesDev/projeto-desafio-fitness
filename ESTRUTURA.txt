ESTRUTURA DO PROJETO - projeto-desafio-fitness (front end)
===========================================================

Aplicacao web em Java (Servlets + JSP) com arquitetura em camadas (padrao
MVC): Servlet (controller) -> Service (regra de negocio) -> DAO (acesso a
API) -> Model (dados). As views sao JSP.

Este projeto NAO acessa banco de dados. Todos os dados vem da API REST
(projeto-desafio-fitness-api), chamada por HTTP com o token JWT do usuario
logado.

Fluxo de uma requisicao:
  Navegador -> AuthFilter -> Controller -> Service -> DAO -> API REST
                   |             |            |         |
                   v             v            v         v
              token da      escolhe JSP   valida    HTTP + JSON
              sessao                      regras    (ApiSingleton)


src/main/java/com/fitness/
----------------------------
model/
    Usuario.java, Desafio.java, Participacao.java, Progresso.java
    Apenas os dados (getters/setters), sem logica. Os nomes dos atributos
    (snake_case) sao os mesmos campos do JSON da API.

dao/
    UsuarioDAO.java, DesafioDAO.java, ParticipacaoDAO.java,
    ProgressoDAO.java, ApiDAO.java (classe base)
    Apenas chamadas HTTP para a API e conversao JSON -> objeto.
    Leitura devolve o objeto (ou null / lista vazia); escrita devolve
    true/false conforme o status da API. Nenhuma regra de negocio aqui.

service/
    UsuarioService.java, DesafioService.java, ParticipacaoService.java,
    ProgressoService.java
    Regra de negocio: validacoes dos formularios, senha minima, filtros
    das listas, total do progresso, etc. Chama o DAO e transforma falhas
    em mensagens (IllegalArgumentException). Nunca lida com
    HttpServletRequest/Response.

controller/
    LoginServlet.java, RegisterServlet.java, LogoutServlet.java,
    HomeServlet.java, UsuarioServlet.java, DesafioServlet.java,
    ProgressoServlet.java, BaseServlet.java
    Ponte entre a rota HTTP e o Service. Le parametros (acao, id), chama
    o Service e decide qual JSP mostrar ou se redireciona.
    BaseServlet e a classe base: so tem metodos utilitarios genericos
    (param, paramLong, paramDouble, paramData, forward, redirect), sem
    regra nenhuma.

filter/
    AuthFilter.java
    Intercepta as requisicoes das telas protegidas e repassa o token JWT
    do usuario logado (guardado na sessao) para o ApiSingleton, que o
    envia no header "Authorization: Bearer <token>" das chamadas a API.

config/
    ApiSingleton.java
    Cliente HTTP unico (padrao singleton) com a URL base da API e o Gson
    configurado para datas. Mexer apenas se mudar o endereco da API.


src/main/webapp/
-----------------
index.jsp
    Redireciona a raiz da aplicacao para o login.

WEB-INF/web.xml
    Configuracao do servlet container.

WEB-INF/jsp/
    Views protegidas, so acessiveis via forward do controller (nao por
    URL direta):
      login.jsp, register.jsp, home.jsp
      usuarios/lista.jsp e usuarios/form.jsp
      desafios/lista.jsp e desafios/form.jsp
      progresso/form.jsp

css/
    Um arquivo por tela (login.css, home.css, ...) e estilo.css (comum).

img/
    Imagens usadas nas telas.


Pastas que NAO devem ser editadas manualmente
----------------------------------------------
target/   -> gerado automaticamente pelo Maven ao compilar (mvn compile/
             package). Qualquer edicao manual e perdida no proximo build.
deploy/   -> artefato de deploy (WAR). Mesma logica do target/,
             nao e codigo-fonte.

Ambas as pastas estao no .gitignore e nao devem ser versionadas no Git.


Outros arquivos na raiz
------------------------
docker-compose.yml -> sobe o Tomcat do front (porta 8081) via Docker.
pom.xml            -> configuracao do Maven (dependencias, build).
README.md          -> como rodar.

Regra geral: cada camada so fala com a camada de baixo dela
(Controller -> Service -> DAO). Nunca pular camada (ex: Controller
chamando DAO direto).
